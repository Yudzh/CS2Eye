# CS2Eye

Это новая техническая основа проекта. Старые функции намеренно не перенесены:
их код остаётся в черновой ветке и возвращается только по мере работы над
конкретными законченными слоями.

## Готовый продуктовый слой

Итерация 01: получение Valve World top-40 из BO3.gg с активной
витриной top-30.

- безопасная проверка источника без изменения БД;
- ручное обновление top-40;
- активны и видимы ровно команды текущего top-30;
- команды на местах 31–40 хранятся как теневые: для них обновляются
  рейтинг, составы и статистика, но они не показываются в витрине;
- выбывшие команды сохраняются, но деактивируются;
- история запусков и рейтинговые снимки;
- исходные ответы для диагностики;
- API и интерфейс со списком команд;
- защита от неполного или противоречивого ответа.

Контракт итерации:
[`docs/ITERATION_01_TOP_TEAMS.md`](docs/ITERATION_01_TOP_TEAMS.md).

Итерация 02: актуальные игроки и тренеры Top-30 с историей составов.

- один запрос деталей для каждой активной команды только к BO3.gg;
- пять игроков и доступные тренеры;
- идемпотентная синхронизация без удаления истории;
- актуальный состав и дата синхронизации в API и UI.

Контракт итерации:
[`docs/ITERATION_02_TEAM_ROSTERS.md`](docs/ITERATION_02_TEAM_ROSTERS.md).

Итерация 05: сравнение двух активных команд текущего Top-30.

- рейтинг, очки и активные составы из БД;
- переиспользование расчёта силы итерации 04;
- относительная сила выбранной пары без трактовки как вероятности;
- сравнение игроков по ролям и детерминированный итог;
- восстановление выбранных команд из URL `/compare?team_a=…&team_b=…`.

Контракт итерации:
[`docs/ITERATION_05_TEAM_COMPARISON.md`](docs/ITERATION_05_TEAM_COMPARISON.md).

Итерация 09: детерминированная сила карт и сравнение map pool.

- сила карты с поправкой на надёжность и минимальной выборкой в три карты;
- прозрачный breakdown общей формы, recent, Top-30 и CT/T;
- раздельная аналитика текущего состава и истории организации;
- сравнение объединённого map pool двух команд без трактовки как прогноза.

Контракт итерации:
[`docs/ITERATION_09_MAP_STRENGTH_AND_MAP_POOL.md`](docs/ITERATION_09_MAP_STRENGTH_AND_MAP_POOL.md).

Итерация 10: H2H организаций и текущих составов.

- два одновременных среза очных карт без попытки собирать BO3-серии;
- отдельный симметричный H2H-рейтинг с весом давности и confidence;
- строгая фильтрация по двум текущим roster ID;
- опыт нынешних игроков, изменения пятёрок и применимость истории;
- typed API и независимый H2H-блок на странице сравнения.

Контракт итерации:
[`docs/ITERATION_10_H2H_ANALYTICS.md`](docs/ITERATION_10_H2H_ANALYTICS.md).

Итерация 11: нормализованные турниры и серии BO1/BO3/BO5.

- несколько `DemoFile` объединяются в один Match без дублирования сущности карты;
- консервативная автоматическая группировка и ручные merge/split/reorder/confirm;
- автоматический счёт и победитель resolved-серии;
- статистика команды по форматам и LAN/playoff/elimination/final;
- H2H одновременно показывает серии и карты, сохраняя прежнюю формулу рейтинга.

Контракт итерации:
[`docs/ITERATION_11_MATCH_SERIES.md`](docs/ITERATION_11_MATCH_SERIES.md).

## Инфраструктура

- FastAPI;
- PostgreSQL 16;
- SQLAlchemy Async;
- Alembic и начальная baseline-миграция;
- React + TypeScript + Vite;
- Docker Compose для локальной разработки;
- pgAdmin;
- liveness/readiness endpoints;
- минимальный UI, проверяющий API и БД;
- базовый backend-тест.

## Чего здесь намеренно нет

- подробного импорта команд и игроков;
- демо-парсинга;
- прогнозов veto, pick/ban и исходов карт или матчей;
- betting draft и прогнозов;
- рыночной аналитики;
- незавершённых страниц и API старого проекта.

### Результаты прогнозов

Страница `/prediction-results` (кнопка «Результаты прогнозов» на главной) показывает
завершённые матчи с сохранённым ML-прогнозом: выбор, вероятность, фактический счёт,
победителя и попадание. Доступны фильтры модели, турнира, уверенности и результата.
Фильтр результата меняет список, а не знаменатель общей точности; прогнозы 50/50
остаются без оценки. Сохранённые предматчевые прогнозы и исторические расчёты
показаны раздельно. Версии моделей при просмотре не пересчитываются.

API: `GET /api/v1/prediction-history/results`. Предматчевые записи берутся из
Prediction History; исторические — из `match_predictions` с источником
`historical_replay`. Архив готового исторического расчёта можно импортировать:

```bash
DEBUG=false .venv/bin/python scripts/import_prediction_replays.py storage/diagnostics/v13/rows.json storage/diagnostics/v13/porto_rows.json
```

Импорт не перезаписывает существующие прогнозы и не создаёт дубли при повторном
запуске. Исходные JSON — локальные диагностические артефакты, в Git не входят.

Ручные факторы команды могут содержать явную поправку вероятности (0–30 п.п.;
0 означает только комментарий) и ограничение конкретным матчем. Поправка
применяется один раз после ML, исходная вероятность показывается отдельно.
Для расчёта на прошлую дату учитываются только поправки, известные к этой дате.
На странице результатов ручной анализ учитывается в основном выборе команды.
Поздние поправки отмечены в карточке и не меняют архивную точность.

Загрузка команды и сравнения: основные данные показываются до завершения тяжёлой
аналитики. `GET /api/v1/analysis/forecast` возвращает Matchup и ML-прогноз за один
расчёт. Общие профили переиспользуются только в рамках запроса (без межзапросного
кэша), события урона суммируются в БД, истории Round Swing состава загружаются
одним пакетом. Формулы и исторические ограничения сохраняются.
Базовое сравнение загружает Round Swing обеих пятёрок одним пакетом. Veto для
расчёта лидерства получает составы серий, действия и результаты карт пакетно;
результаты карт читаются без тяжёлых JSON-полей. Одна ручная поправка
сериализуется один раз для списков relevant/all_active в пределах ответа.
Расчётное veto также загружает Round Swing обеих пятёрок пакетом; Map Strength V3
читает только нужные поля раундов и убийств без JSON состояний раунда. Это ускоряет
сбор общего контекста карточки бота и AI-анализа.

Telegram-бот использует тот же backend, активную ML-модель и ручные поправки.
При открытии матча сразу появляются данные матча и кнопки; текущий прогноз
добавляется после отдельного `GET /api/v1/analysis/match-card-context`. Полный
контекст аналитики загружается при первом открытии подробного раздела и
переиспользуется между разделами. Карточка и подробности имеют отдельные кэши;
«Обновить данные» сбрасывает оба. Запоздавшие ответы не меняют выбранный раздел.
Общая оценка качества полного AI-контекста отображается только в полном контексте.
Карточки матчей переиспользуются до 30 секунд; кнопка «Обновить данные» обходит
этот кэш. Списки турниров/матчей обновляются через API с TTL 60/45 секунд,
последний AI-анализ всегда запрашивается заново. Telegram показывает только сохранённые AI-отчёты и не запускает генерацию.
Если отчёта нет, бот сообщает об этом без предложения его создать. В карточке видны версия модели и время расчёта;
сохранённый AI-анализ отмечен временем создания. Для аналитики отведено до
120 секунд ожидания, обычные запросы используют `CS2EYE_API_TIMEOUT_SECONDS`.

После изменения кода работающий polling-процесс нужно перезапустить:

```bash
sudo docker compose -f compose.local.yml restart bot
```

Предматчевые прогнозы сохраняются серверной фоновой задачей раз в минуту,
как только у запланированного матча известны обе команды. Ожидать даты или
времени начала не требуется. Открытие карточки матча также запускает сохранение.
Сохранённый прогноз возвращается без пересчёта. Ошибки автоматического сохранения
записываются в серверный журнал, попытки повторяются каждую минуту до старта.
Задача работает при запущенном API и использует матчи из сохранённого расписания.
После обновления требуется `alembic upgrade head` и перезапуск API.

Страница `/predictions` объединяет прогнозы на предстоящие и сыгранные матчи.
На главной она открывается кнопкой «Прогнозы». Вкладка «Предстоящие» показывает
все известные пары, включая матчи без сохранённого прогноза; «Сыгранные» —
сохранённый выбор, вероятности, счёт и оценку. Восстановленные прогнозы отмечены
в списке, их точность считается отдельно. Поиск, турнир и дата фильтруют обе
вкладки; результаты можно отфильтровать по попаданиям и ошибкам. Список
обновляется раз в минуту. Старый `/prediction-results` открывает «Сыгранные».
`/prediction-history` остаётся подробной диагностикой моделей.

### AI-отчёты: локальная генерация и просмотр на сервере

AI-отчёты создаются через локальный веб-интерфейс/API с Ollama и сохраняются
в PostgreSQL вместе с контекстом анализа. Telegram только читает готовые отчёты;
старые кнопки генерации открывают сохранённый отчёт, перегенерация отключена.
На сервере для просмотра достаточно `MATCH_LLM_ENABLED=false`: Ollama и GPU
не нужны, сохранённые отчёты остаются доступны.

Бот читает базу того API, который указан в `CS2EYE_API_BASE_URL`.
При первом переносе приложения нужно перенести и базу PostgreSQL: отчёты
не хранятся в Git или только в файлах Ollama. Последующие отчёты, созданные
в отдельной локальной базе, автоматически на сервер не попадут.
Для последующей локальной генерации можно подключить локальный API к серверной
PostgreSQL через SSH-туннель (`DATABASE_URL`), оставив Ollama локальной.
При этом используются серверные матчи и их ID; серверная БД не публикуется
в интернете. Локальный и серверный API должны использовать совместимые
версии схемы БД. Автоматическая синхронизация отдельных баз не реализована.

### Хранение исходных демок

В форме загрузки новых демок по умолчанию включены парсинг и удаление исходника
после успешного сохранения результатов в PostgreSQL. Опции можно отключить.
Ошибка парсинга сохраняет исходник для повторной попытки; неизменённые файлы
старого архива при такой загрузке не включаются в задачу удаления.
Части разделённых демок сохраняются для последующей сборки продолжения матча
(диагностика `source_retained_split_demo`). Массовый парсинг старого архива
по умолчанию не удаляет исходники: `DEMO_DELETE_AFTER_SUCCESSFUL_PARSE=false`.
Для VPS с 4 ГБ RAM используйте `DEMO_PARSE_CONCURRENCY=1`; память и размер
PostgreSQL нужно контролировать на реальных демках. Удаление исходников
уменьшает расход диска, но не требования к памяти самого парсера.
