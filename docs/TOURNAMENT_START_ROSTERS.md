# Проверка составов на старте турнира

Реализация в ветке `telegtam-prod`. Проверка относится к участнику турнира, а не к матчу. Проверки из построения анализа/прогноза удалены. Матчевые Lineups и новости не запрашиваются.

## BO3: запрос и отбор

Используется существующий `Bo3Client.fetch_team(team.bo3_id, team.bo3_slug)`:

```http
GET https://bo3.gg/api/v1/teams/{slug}
Referer: https://bo3.gg/teams/{slug}
```

Базовый URL берётся из `settings.bo3_site_base_url`. Клиент сохраняет существующие сетевые таймауты, настройки соединения и три попытки запроса. Проверяет соответствие ID/slug команды и отсутствие дублирующихся BO3 ID участников.

Из `players` принимаются только участники, у которых одновременно:

- `is_coach is False`;
- `is_substitute == False`;
- `status == 1` (активный участник);
- `team_id` совпадает с ID команды в ответе;
- положительный BO3 ID.

Тренеры, bench (`status == 2`), неизвестные статусы и участники другой команды исключаются. Результат должен содержать ровно пять уникальных игроков: список не обрезается до пяти. Правила активной принадлежности соответствуют существующей интеграции (`TopTeamsService`); рейтинговая пятёрка при этой проверке не используется. BO3 ID сопоставляется с `Player.bo3_id`, в снимке хранятся локальные `Player.id`. Для нового игрока создаётся отдельная запись Player без переноса его в основной состав команды.

Живая проверка в ходе реализации: `GET https://bo3.gg/api/v1/teams/vitality`, BO3 team ID `667`; ответ содержал 6 участников. Отобраны:

## Автоматический запуск

В lifespan API запускается фоновая asyncio-задача. Она проверяет дату сразу при старте API и затем каждые 900 секунд. Календарный день определяется в UTC. Для работы автоматизации API должен быть запущен, а миграции применены.

В дату `start_date` проверяются все `TournamentTeam`. При перезапуске API пропущенные проверки догоняются для турниров, которые ещё не закончились. Если `end_date` отсутствует, автоматический запуск ограничен датой старта. Ошибки повторяются на следующем проходе; успешные ответы больше не запрашиваются. Ручная кнопка запуска/повтора сохранена. До даты старта она возвращает `not_due`, чтобы ранний запрос не зафиксировал устаревший состав вместо проверки в день старта.

## Хранение и использование

`TournamentRosterCheck` уникален по `(tournament_id, team_id)` и хранит исходные IDs, полную BO3-пятёрку, добавленных и отсутствующих игроков, статус, URL источника, время последней попытки и ошибку. Исходный состав читается до запроса BO3 и сохраняется при неуспешных попытках. Успешный снимок фиксируется один раз. Статус `changed` вместе со списками является записью об изменении состава в контексте турнира. Попарные замены автоматически не создаются, постоянный переход и временная замена из несовпадения не выводятся.

Неполный/некорректный ответ получает `partial`, ошибка запроса — `error`; успешный снимок и списки изменений при этом не записываются. Импорт игроков и состава выполняется в savepoint. PostgreSQL-блокировка строки турнира сериализует параллельные ручные/автоматические проверки; уникальное ограничение дополнительно защищает от дублей.

Основной `Team.current_roster_id` не изменяется. Вспомогательные TeamRoster с источником `tournament` нужны расчётам статистики и исключены из выбора основного состава по датам. Явное последующее назначение такого состава основным переводит его в соответствующий основной источник.

`EffectiveRosterService` передаёт сохранённую пятёрку в Team Strength и Map Strength. Контекст турнира/матча передаётся в обычных, исторических и проецируемых турнирных прогнозах, включая comparison fallback. Даты расчёта согласованы. Новый игрок рассчитывается через существующий Player Strength со своей доступной статистикой. Team Strength использует идентичность турнирной пятёрки также для статистики исполнения и результатов. Map Strength использует те же player IDs для применимости истории и тот же контекст для базового Team Strength.

Активные ручные overrides сохраняют приоритет; конфликт с BO3 виден в результатах и предупреждениях. Штраф применяется только для установленных `MANUAL`/`CONFIRMED` замен, один раз в Team Strength; `DETECTED` и сам BO3-снимок штрафа не создают. Подтверждённая замена, уже присутствующая в BO3-пятёрке, не теряет установленный штраф. Новая фиксация помечает прежние турнирные прогнозы устаревшими.

Снимок действует только в контексте своего турнира и его дат. После окончания он остаётся доступен в истории, включая отдельное поле BO3-пятёрки в интерфейсе, и не подменяет основной состав для будущих турниров.

## Проверка искусственного изменения на реальных данных

Повторяемая проверка: `DEBUG=false PYTHONPATH=src .venv/bin/python scripts/verify_tournament_roster_change.py`.

Скрипт использует настроенную PostgreSQL и настоящий BO3. Во внешней транзакции создаёт временный турнир, подставляет ZywOo вместо Artfr0st в исходную пятёрку 1win и вызывает настоящие POST/GET-обработчики приложения через ASGI. Endpoint `commit()` ограничен savepoint; в `finally` откатывается внешняя транзакция. Отдельный запущенный сервер не вызывается, поскольку его транзакции невозможно включить в этот откат.

Фактический результат: `changed`, добавлен Artfr0st, отсутствует ZywOo, штраф `0`. GET возвращает полную настоящую пятёрку BO3. Повторный POST не создаёт дубликат и не делает второй запрос BO3. После отката отдельным подключением подтверждены исходный `current_roster_id`, отсутствие временного турнира и исходное количество записей проверок. Заглушка в данных не остаётся.
