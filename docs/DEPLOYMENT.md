# Первый сервер CS2Eye

Схема: VPS запускает сайт, API, PostgreSQL и бота. Ollama остаётся на компьютере.
Сайт и весь внешний API закрыты HTTP Basic Auth в Nginx. Бот обращается к API
по внутренней сети Docker. Порты API и БД наружу не публикуются.

Первый запуск без домена: сайт слушает только `127.0.0.1:18080` сервера,
доступ с компьютера через зашифрованный SSH-туннель. Пароль сайта — дополнительная
проверка. Для этой схемы домен и сертификат не нужны. Публичный доступ по домену
потребует отдельной настройки HTTPS; не меняйте привязку на `0.0.0.0` ради HTTP.

## 1. До покупки VPS

Проверить размер PostgreSQL и запас для роста. Удаление исходников не уменьшает
сохранённые события в БД. Архив старых демок оставляем на компьютере.
Для старта рассматриваем 2 vCPU / 4 ГБ RAM, но реальное потребление парсера нужно
проверить: один файл может потребовать больше доступной памяти. В production
установлена параллельность 1; если памяти мало, парсинг выполняем локально.

## 2. Подготовка сервера

Установить Docker Engine с Compose plugin. Создать пользователя с SSH-ключом,
настроить SSH-доступ и оставить открытым только необходимый SSH-порт.
Перенести проект без `.env`, `.venv`, `node_modules`, архива демок и секретов.
Работать из корня проекта. Production запускается отдельным Compose-проектом,
его тома не совпадают с локальными.

## 3. Секреты на сервере

```bash
cp .env.prod.example .env.prod
chmod 600 .env.prod
mkdir -p deploy/secrets backups
chmod 700 deploy/secrets backups
```

В `.env.prod` вписать токен бота и новый пароль PostgreSQL. Для URL подключения
используйте пароль из hex-символов, например результат `openssl rand -hex 32`.
Не используйте значения из локального `.env` автоматически.

Создать пароль сайта интерактивно (на Ubuntu нужен пакет `apache2-utils`):

```bash
htpasswd -cB deploy/secrets/web.htpasswd owner
chmod 644 deploy/secrets/web.htpasswd
```

Пароль хранится в виде хеша. Каталог доступен только владельцу на хосте;
файл должен читаться Nginx внутри контейнера. В Git секреты не попадают.
Для смены пароля повторить `htpasswd` без `-c`, затем пересоздать `webui`.

## 4. Перенос данных

Сначала сделать резервную копию локальной PostgreSQL через `pg_dump -Fc`.
Перед окончательной копией приостановить изменения данных. Восстановление
проверить на отдельной базе; исходную локальную базу не удалять.

На сервере сначала собрать образы и поднять только БД:

```bash
docker compose --env-file .env.prod -f compose.prod.yml config --quiet
docker compose --env-file .env.prod -f compose.prod.yml build
docker compose --env-file .env.prod -f compose.prod.yml up -d db
```

Дождаться healthy у БД, затем восстановить перенесённый `backups/local.dump`:

```bash
docker compose --env-file .env.prod -f compose.prod.yml exec -T db sh -c 'pg_restore --no-owner --no-acl --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backups/local.dump
```

Команда предназначена для пустой базы при первом переносе. Если восстановление
оборвалось или сервер уже содержит данные, не запускайте её повторно вслепую.
Без восстановления новая БД будет пустой; миграции не переносят статистику.
Исходные файлы старых демок остаются локально, поэтому их повторный парсинг
с сервера недоступен. Существующая аналитика читает результаты из БД.

## 5. Запуск и вход

Остановить локальный polling-процесс бота с тем же токеном, затем:

```bash
docker compose --env-file .env.prod -f compose.prod.yml up -d
```

На компьютере, заменив пользователя и адрес:

```bash
ssh -N -L 18080:127.0.0.1:18080 user@SERVER_IP
```

Открыть `http://localhost:18080`, войти как `owner` с созданным паролем.
Туннель должен оставаться открытым во время работы. Telegram работает независимо.
Проверить через туннель: без пароля `/` и `/api/v1/health/ready` возвращают 401;
с паролем доступны сайт и API, в боте доступны матчи и сохранённые AI-отчёты.
Перезапуск контейнеров должен сохранять БД. Не выполнять `down -v`.

## 6. Резервные копии и обновления

Для сервера `82.146.63.83` обновления выполняются командой `cs2eye-deploy`
по [инструкции Git-деплоя](GIT_DEPLOYMENT.md). Команды ниже относятся
к исходной установке до перехода на каталоги релизов.

Пример ручной копии на сервере:

```bash
docker compose --env-file .env.prod -f compose.prod.yml exec -T db sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > backups/server.dump
```

Копию скачивать на другой компьютер; файл на том же VPS не защищает от потери
сервера. Перед регулярной эксплуатацией настроить расписание, хранение нескольких
версий и проверить восстановление. Эта конфигурация сама расписание не создаёт.

Перед обновлением сделать копию, затем:

```bash
docker compose --env-file .env.prod -f compose.prod.yml build
docker compose --env-file .env.prod -f compose.prod.yml run --rm migrate
docker compose --env-file .env.prod -f compose.prod.yml up -d
```

Не увеличивать число API workers: каждый запускает фоновые задачи и держит
состояние задач парсинга в своей памяти. Миграции с изменением схемы проводить
в окно обслуживания, при необходимости предварительно остановив API и бота.

## 7. Локальный AI после переезда

Генерация через сервер отключена (`MATCH_LLM_ENABLED=false`), чтение отчётов
остаётся доступным. Локальный генератор должен записывать в серверную БД через
защищённое подключение, используя её ID матчей. Отдельная локальная БД сама
не синхронизируется. Подключение локального API к БД через SSH и координацию
его фоновых задач настраиваем после первого переноса; PostgreSQL наружу не открыт.

## Доступ по домену cs2eye.ru

Вместо SSH-туннеля можно использовать профиль `https`. Nginx продолжает
запрашивать пароль и для сайта, и для API; Caddy добавляет автоматический HTTPS.

1. В DNS-панели домена добавить A-запись `@` → публичный IPv4 VPS.
   Не указывать чужой адрес из парковочной страницы регистратора. Если есть
   AAAA-запись, она должна вести на работающий IPv6 этого VPS, иначе удалить её.
   Почтовые записи MX/TXT не менять. `www` пока не нужен.
2. Дождаться, когда `dig +short A cs2eye.ru` возвращает адрес VPS.
3. Открыть входящие TCP 80 и 443 в панели провайдера и firewall сервера,
   сохранив SSH-доступ. Порты БД и API не открывать.
4. После переноса базы и создания файла паролей запустить:

```bash
docker compose --env-file .env.prod -f compose.prod.yml --profile https up -d
```

Caddy получает и продлевает сертификат, HTTP перенаправляет на HTTPS.
Данные сертификатов сохраняются в томе `caddy_data`; не удалять его при обновлении.
Открыть `https://cs2eye.ru` и проверить запрос пароля. Без пароля должны
возвращать 401 и сайт, и `https://cs2eye.ru/api/v1/health/ready`.

Проверка журналов сертификата:

```bash
docker compose --env-file .env.prod -f compose.prod.yml --profile https logs --tail 50 https
```

В дальнейших командах `up` использовать `--profile https`. SSH-туннель остаётся
резервным доступом, веб-порт 18080 по-прежнему привязан только к localhost VPS.

## Исходящий прокси для BO3

Если VPS не может подключаться к BO3, в `.env.prod` можно задать
`BO3_PROXY_URL=http://USER:PASSWORD@PROXY_HOST:PORT` или SOCKS5 URL.
Прокси применяется только к клиенту BO3; внутренний API бота и PostgreSQL
продолжают работать напрямую. Пустое значение сохраняет прежнее поведение.
Пароль со специальными символами в URL должен быть percent-encoded.
Не публикуйте URL с учётными данными и не выводите полный `compose config`.

Нужен действующий внешний прокси с доступом к BO3. Прокси на том же VPS
без другого исходящего маршрута сам по себе проблему доступа не решает.
`127.0.0.1` внутри API-контейнера означает этот контейнер, а не компьютер
владельца или хост VPS. Локальный VPN на компьютере не передаётся на VPS.

После изменения исходников сначала перенести новые файлы приложения и Compose,
затем пересобрать и пересоздать только API:

```bash
docker compose --env-file .env.prod -f compose.prod.yml build api
docker compose --env-file .env.prod -f compose.prod.yml up -d --no-deps api
```

Простой `restart` не применяет новые переменные окружения контейнера.
После запуска проверить обновление команд; работоспособность конкретного
прокси определяется реальным запросом BO3, поддержка конфигурации этого
не гарантирует.

### AdGuard SOCKS и существующий образ API

При AdGuard VPN CLI на хосте в SOCKS-режиме привязать listener к внутреннему
адресу Docker bridge с авторизацией. Сохранить BO3_PROXY_HOST, BO3_PROXY_USER,
BO3_PROXY_PASSWORD в .env.prod (случайный hex-пароль). Не открывать порт 1080
на публичном интерфейсе. Проверить, что listener запущен после настройки.

`compose.bo3-proxy.yml` подключает ALL_PROXY только к API, что работает и с
ранее собранным образом через HTTPX trust_env. NO_PROXY исключает внутренние
адреса. Если используется новая настройка BO3_PROXY_URL, она имеет приоритет;
не задавать две разные конфигурации одновременно. ALL_PROXY влияет и на
другие внешние HTTPX-запросы внутри API, если такие появятся.

Для пересоздания API и последующих запусков использовать оба файла:

```bash
docker compose --env-file .env.prod -f compose.prod.yml -f compose.bo3-proxy.yml up -d --no-deps api
```

Подключение AdGuard и автозапуск после перезагрузки нужно проверить отдельно.
При остановке прокси BO3 будет недоступен; сохранённая аналитика остаётся в БД.

### Telegram через AdGuard

Если Telegram недоступен напрямую (таймаут на `set_my_commands`), обновлённый
`compose.bo3-proxy.yml` задаёт для бота `TELEGRAM_PROXY_URL`. Требуется версия
приложения с `AiohttpSession(proxy=...)` и зависимостью `aiogram[proxy]`.
Одного ALL_PROXY для aiogram недостаточно. HTTP-клиент внутреннего API бота
не получает настройки прокси. После обновления пересобрать образ bot и
пересоздать его с обоими Compose-файлами; простой restart код не обновляет.
